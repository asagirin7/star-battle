# 人間の所要時間からStar Battleの盤面難易度を推定する研究メモ

2026-10-23。本人の定義は「人間が解くのに時間がかかるほど難しい」。
ここでは評価器・生成器の研究を行い、公開版の配点、自動×、生成条件、時間計測は変更しない。

## 結論

難易度の目的変数を「基準となる習熟度の人が初見で解くときの、画面を見て取り組んでいる時間」に置く。
同じ人でもばらつくため、予測中央値と不確かさを扱う。最初は盤面の難しさの順位を当てることを目指し、実測前に「この盤面は3分」と断定しない。

時間には発見、推論、入力のすべてを含める。そのうえで画面サイズ、入力方法、自動×設定、プレイヤーの習熟度を揃える/補正する。
大きい盤面で入力だけが増えて時間が延びることも本人の定義では負担の一部だが、同じサイズ内での予測精度も別に評価する。

## 一次資料で確認できたこと

1. Pelánek (2014), *Difficulty Rating of Sudoku Puzzles: An Overview and Evaluation*。
   人の所要時間を使った評価で、個々の論理解法の複雑さと、推論どうしの依存関係の両方を扱う。
   同じ簡単な解法だけで解ける盤面でも、次に進める箇所の多さによって難しさを区別する考え方がある。
   数独での知見なので、その係数や精度をそのままStar Battleへ移すことはできない。
   https://arxiv.org/html/1403.7373v1

2. He et al. (2026), *Evaluating SAT Solver Metrics as Predictors of Human-Perceived Nonogram Difficulty*。
   ノノグラムのユーザー調査では、SATソルバーの指標と、人の行動・自己申告の難しさとの有意な対応を確認できなかった。
   一般的な機械の探索量を、人の時間の代わりに採用する根拠にはならない。プレプリントであり、対象はStar Battleではない。
   https://arxiv.org/html/2608.23300v1

3. masonomara/star-battle は、人が説明できる解法とルール使用に基づく難易度付けを実装している。
   実装設計の参考にはなるが、READMEで人間の所要時間に対する検証までは確認できていない。
   https://github.com/masonomara/star-battle

以下はこれらを踏まえた、このアプリへの提案・仮説であり、実証済みのStar Battle評価器ではない。

## 現コードを調べて分かった制約

- logic_solver.py の rounds は、複数の色/行/列を走査したループ回数。
  一つのループ内で前の排除結果を次の色へ伝えるため、並び順に依存する。
  「人間の推論1手」や「推論の依存関係の深さ」ではない。
- 共通禁止とHall型排他性をまとめて計算するので、なぜそのマスが消えたかという説明単位の履歴は現在ない。
  また、同じ排除を簡単な形状ルールと大きい集合ルールの両方で説明できる場合がある。
- Clear.seconds と表示タイマーは started_at からの実経過時間で、閉じた時間や別端末での中断も含む。
  完了したClearだけでは、途中退出と失敗を含めた母集団も復元できない。
- 新しい盤面を各プレイヤーに生成する現在の方式では、同一盤面の複数人による時間がほとんど集まらない。
  アカウントと共有URLは比較実験に使えるが、友人への共有だけだと参加者が偏る。

### 小実験: 色番号を変えただけで rounds は変わる

scripts/research_difficulty.py を現在の生成器・ソルバーで実行した。
5難易度×5seed=25盤面、各盤面で20通りの色ラベルの置換を試した。
候補の形と一意な星位置は変えず、全500回で解答の一致を確認した。

- 25盤面中16盤面で rounds が変動した。
- 同じ盤面で最大3ループの差が出た。
- 7×7の例では2〜4ループになった。

生データ: difficulty-probe.json。
再現: .venv/bin/python scripts/research_difficulty.py
生成器に時間制限があるため、非常に遅い実行環境では同じseedでも生成結果が変わる可能性がある。

これは現カウンターの走査順依存を示す。色や向きが人の見つけやすさへ与える影響を測った実験ではなく、
人間の難易度との相関を確認したものでもない。roundsをそのまま配点や難易度に使わない理由にはなる。

## 評価器で記録したい特徴

| 特徴 | 人の時間との関係についての仮説 |
| --- | --- |
| 簡単な次の推論の数 | 進める箇所が一つしかないと、発見に時間がかかる |
| 次の推論を見つけるまでの候補走査量 | 関係ない色・行も多く確認するほど探索が長くなる |
| 必要なルールの種類と範囲 | 複数の色/行を同時に保持する負担が増える |
| 推論の依存関係の深さ | 一つの発見から次の発見を待つ連鎖が長いほど進行が遅くなる |
| 瓶頸の長さと位置 | 序盤・中盤で単独の発見に詰まる時間が全体を支配しうる |
| 関係セルの距離・色の分断された候補・境界の形 | 視覚的な追跡が難しくなる可能性がある |
| ルール適用と入力の総量 | 単純な盤面でも操作量が増えると総時間は延びる |

まずは「ルール適用数」「次の簡単な手の少なさ」「推論の依存関係」の3つに絞る。
見た目の特徴やセットの大きさが本当に時間を説明するかは実測で選ぶ。

評価専用の解き手は、現在の候補状態から説明可能な操作を列挙し、最も簡単なルールを優先する。
同じ結論の別証明を次の手として重複カウントしない。候補星の仮置き、分岐、保存解の参照は行わない。

複数の解き順をサンプルし、典型的な手順の統計と、見つかった簡単な解き筋の両方を記録する。
一つの固定順の結果だけで盤面を評価しない。「最短の解き筋を完全に求めた」とも扱わない。
集合の補集合を使った等価な証明や、一度に複数のマスが消える操作も正規化する。

## 人の実測で校正する方法

最初の小規模パイロット案:
同サイズの初見盤面20〜30枚を用意し、参加者が複数枚、各盤面も複数人に当たるよう割り当てる。
まず1盤面あたり10件前後を目安に集めるが、必要数や予測精度を保証する根拠ではない。
盤面が複数プレイヤーにまたがるようにして、プレイヤー速度と盤面難易度を区別する。

記録候補:
- 盤面ID、プレイヤーID、初見/再挑戦、提示順、モデル・UIのバージョン
- 表示中の時間、非表示・明示的中断の区間、入力の時刻、クリア/ミス失敗/退出
- サイズ、難易度モード、端末と入力方法、自動×設定
- 可能なら各星を確定するまでの時間。メモの操作は思考の直接の観測とは扱わない

無操作時間を一律30秒で切らない。考えている時間を消してしまうため。
自動テストや既知のAIプレイは研究標本から分離するが、「速いからAI」とは判定しない。
9×9は1ミス失敗なので、生き残ったクリアだけを平均すると選択の偏りが出る。
退出は途中までの観測、ミス終了は別の終端事象として残す。すべてを単純に同じ打ち切りとせず、終了理由を区別する。

初期の推定案:
log(表示中の所要時間) = 盤面の効果 - プレイヤーの速さ + 端末/自動×/練習の効果 + 誤差
という階層モデルを出発点にする。未完了と失敗の扱いは別途感度分析し、クリア時間だけで難しさを断定しない。

未知の盤面を予測するには、その盤面の効果を上記の解法特徴から推定する。
盤面を分けた検証と、未参加プレイヤーに対する検証を行い、同じ盤面や同一形の回転/反転が学習と評価へ混ざらないようにする。
サイズだけ・手数だけの基準と比較し、順位相関、予測時間の誤差、予測区間の当たり方を報告する。
同じサイズ内、プレイヤー習熟度別でも評価する。

## 指標からの生成

初期は「説明可能な解法の特徴を狙う生成」であって、「人間が必ず5分かかる生成」ではない。
人のデータが揃ってから、基準プレイヤーの予測時間帯を狙う生成へ進める。

1. 候補の盤面を生成する。
2. 連結・一意解・singleton禁止などのモード条件と、仮置きなしの解法による完遂を必須条件として検査する。
3. 評価専用の解き手から特徴を得て、所要時間と不確かさを予測する。
4. 目標の時間帯へ近づくよう色の境界を少しずつ変更し、必須条件と指標を再検証する。
5. 解配置・形状の多様性も保ち、似た盤面だけを連続採用しない。
6. 生成で極端に高い予測値になった盤面は、評価器の弱点を突いただけの可能性もあるため人が確認する。

無料枠のAPI応答で重い探索を毎回行うより、事前生成・採点した候補を蓄え、出題時は軽い検証と選択にするのが実装案。
具体的な予測時間・閾値・点数への換算はまだ決めない。自動×にはこれらの解法を追加しない。
